## 1. Knox SSO 운영 조직

> 배경 설명(공통): 사내 CI/CD 포털(ToolHub, khtoolhubw02)에 웹 서비스 4종
> (Studio/CICD dashboard/Release/SignTool)을 운영 중이며, Knox SSO 연동을
> 준비하고 있습니다. Jira·GHE(github.samsungds.net)와 동일한 방식의 연동을
> 목표로 합니다.

**K1. 신규 서비스 연동 신청 절차와 리드타임** — *Phase 1 전 필수*

1. 신규 서비스(사내 웹 포털)의 Knox SSO 연동 신청은 어느 조직/시스템으로 하면 됩니까?
2. 신청 시 필요한 제출 정보 목록을 알려주십시오.
   (당사 준비 정보: 서비스 URL 1개 호스트(khtoolhubw02), 하위 경로 4개
   — /studio, /dashboard, /release, /signtool — 각각의 콜백 주소)
3. 신청부터 연동 완료까지 통상 리드타임은 어느 정도입니까?
4. 하나의 호스트에 여러 하위 서비스 경로가 있는 경우, SP(서비스) 등록을
   1건으로 묶을 수 있습니까, 경로별 개별 등록입니까?

**K2. 연동 프로토콜** — *Phase 3 전 (Apache 모듈 선정에 필요)*

1. 신규 서비스 연동 시 지원 프로토콜은 무엇입니까? (SAML 2.0 / OIDC / 기타)
2. Jira·GHE가 현재 연동된 프로토콜은 무엇입니까? (동일 방식 선호)
3. 리버스 프록시(Apache) 레이어에서 인증을 일괄 처리하는 구성
   (mod_auth_mellon 또는 mod_auth_openidc)에 제약이 있습니까?
4. 연동 불가 판정 시 AD LDAP 직접 조회(mod_authnz_ldap)가 정책상 허용됩니까?

## 2. GHE 관리 조직 (github.samsungds.net)

> 배경 설명(공통): 사내 웹 서비스가 사용자 본인 명의로 GHE에 커밋/push 및
> workflow_dispatch 호출을 수행하려 합니다(사용자 ≤7명, 전원 대상 repo
> write 권한 보유). 봇 계정이 아닌 **사용자 본인 신원**을 유지하는 것이
> 설계 원칙입니다.

**G1. OAuth App 등록** — *Phase 2 전 필수*

1. 사내 조직(org) 또는 개인 계정으로 OAuth App을 등록할 수 있습니까?
2. 등록에 관리자 승인 절차가 필요합니까? 필요하다면 절차와 리드타임은?
3. OAuth App의 callback URL로 사내망 호스트(khtoolhubw02)를 지정하는 데
   제약이 있습니까?

**G2. OAuth 토큰 정책** — *Phase 2 전*

1. OAuth App으로 발급된 access token의 만료 기간은 얼마입니까?
2. refresh token이 지원됩니까? 지원 시 만료 정책은?
3. OAuth access token으로 git https push가 가능합니까?
   (x-access-token 방식 — 실환경 테스트 계획 있음, 정책상 제약 여부 확인)

**G3. fine-grained PAT (폴백 대비)** — *Phase 2 전*

1. 현재 GHE 버전에서 fine-grained PAT이 지원됩니까?
2. 지원 시, 대상 repo 한정 + Contents(RW)/Actions(RW) 권한 부여가 가능합니까?
3. 미지원 시 classic PAT 사용에 대한 사내 보안 지침이 있습니까?

## 3. AWS / 클라우드 담당

> 배경 설명(공통): 사내에서 AWS Bedrock(Claude)을 CLI로 사용 중이며, 웹
> 서비스에서 동일하게 **사용자 본인 AWS SSO 신원**으로 Bedrock을 호출하려
> 합니다(SSO OIDC device authorization flow, CLI `aws sso login`과 동일 방식).

**A1. SSO 세션 수명** — *Phase 1 전 필수 (재승인 UX 빈도 결정)*

1. AWS IAM Identity Center(SSO) access token의 수명은 얼마로 설정되어 있습니까?
2. SSO 세션(재승인 없이 토큰 갱신 가능한 기간)의 수명은 얼마입니까?
3. 역할 임시 자격증명(GetRoleCredentials)의 수명은 얼마입니까?

**A2. Knox/AD 페더레이션** — *Phase 1 전 (승인 클릭 횟수 예측)*

1. AWS SSO 로그인이 사내 AD/Knox와 페더레이션되어 있습니까?
2. 페더레이션 상태에서 device flow 승인 시 사용자에게 요구되는 절차는
   무엇입니까? (자동 승인 / 클릭 1회 / ID·PW 재입력)

**A3. 비용 집계** — *Phase 3 전 (정산 리포트 소스 결정)*

1. 현재 CLI 사용자별 Bedrock 비용은 어떤 기준으로 집계됩니까?
   (CloudTrail 신원 / 태그 / 계정 분리 등)
2. 동일 신원으로 호출하는 웹 서비스 사용량이 기존 집계에 자동 합산됩니까?
3. 사용자별 정산 리포트를 뽑을 수 있는 데이터 소스는 무엇입니까?

## 4. 보안 조직

> 배경 설명(공통): 사내 도구 코드의 수정·생성을 보조하는 웹 서비스를
> 준비 중입니다. 사용자가 첨부한 요구조건 문서와 사내 코드 분석 요약이
> AWS Bedrock으로 전송되며, 생성된 코드는 사람 리뷰 승인 후 사내 CI에서
> 검증됩니다. 코드의 Bedrock 전송은 기존 CLI 사용 선례가 있습니다.

**S1. 데이터 반출 등급** — *파일럿 전 필수*

1. 고객/사내 요구조건 문서(정형·비정형)를 Bedrock으로 전송하는 것이
   허용되는 데이터 등급 기준을 알려주십시오.
2. 전송 전 필수 처리(등급 표시 확인, 마스킹 등) 요건이 있습니까?
3. 문서 유형별(사내 작성 문서 vs 고객 제공 문서) 기준 차이가 있습니까?

**S2. 보안/AI 심의** — *오픈 전*

1. CLI 개인 사용을 넘어 "공식 사내 서비스"로 운영할 경우 보안 심의 또는
   AI 서비스 심의 대상입니까?
2. 대상이라면 심의 절차, 필요 문서, 리드타임을 알려주십시오.

**S3. SignTool 행위 로그 요구 수준** — *Phase 3 전 (감사 규약 설계에 필요)*

1. 코드 서명 행위 기록의 필수 보존 기간은 얼마입니까?
2. 감사 대상 범위(서명 요청자/승인자/대상 파일/결과)에 대한 사내 기준이
   있습니까?
3. 로그 위변조 방지 요건(별도 저장소, WORM 등)이 있습니까?
